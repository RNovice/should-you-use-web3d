# 你的專案該不該引入 Web 3D？

一份前端技術研究，做成**網頁式簡報**：少量的投影片穿插可實際操作的頁面，
所有數字都在你的瀏覽器當場量出來，不是截圖。

## 這份研究在問什麼

Web 3D（WebGL / Three.js / React Three Fiber）這幾年成熟得很快，
一百萬個節點在瀏覽器裡跑 60fps 已經不是問題。

於是問題不再是「做不做得到」，而是 **「該不該做」**。

這份研究拿一個真實的企業級 SaaS 產品當題目，做了三個 PoC，
試圖回答一個可以被別人重複使用的問題：

> 什麼情況下，把一個介面從 2D 換成 3D 是對的？
> 什麼情況下它只是把成本換了個位置？

## 結論

**這個產品先不引入 Web 3D。**

技術面全部達標——一百萬節點 60fps、2～4 個 draw call、佈局 108ms、不需要 Web Worker。
但三個 PoC 的產出物都是「一張要被看懂的圖」，而 Web 3D 的價值在
「一個要被操作的工具」。

值得強調的是這不是「技術做不到」的報告，是 **「做得到但不該做」** 的報告——
負面結果比正面結果難寫，也更有用。

需求本身是存在的，只是不在這條產品線上：同樣的技術，
在需要停留與互動的產品（產品組態器、沉浸式廣告、WebXR）上是賣點，
在需要閱讀與決策的工具上是成本。

## 帶走的三個問題

研究真正的產出不是結論，是判準——個案會過時，判準不會：

1. **使用者是「看」還是「操作」？** 看 → 2D。操作 → 才往下問。
2. **把互動拿掉之後，價值還剩多少？** 剩很多 → 那它其實是一張圖。
3. **現在的瓶頸是「畫不動」還是「看不懂」？** 畫不動先換渲染層，看不懂才考慮換維度。

這三個問題花不到五分鐘，但它們擋掉了本研究裡的三個 PoC，每一個都是。

## 幾個實測數字

**渲染（M 系列 Mac / Chromium）**

| 節點數 | FPS | Draw calls | 佈局耗時 | 渲染策略 |
|---|---|---|---|---|
| 2,331 | 60 | 4 | 34 ms | InstancedMesh |
| 10,000 | 60 | 4 | 122 ms | InstancedMesh |
| 100,000 | 60 | 2 | 459 ms | InstancedMesh |
| 1,000,000 | 60 | 2 | 108 ms | Points |

**天花板是三角形預算，不是 draw call。** 一開始一百萬節點直接把分頁打掉——
最低面數的 icosahedron 也有 20 個三角形，一百萬顆就是每幀兩千萬個三角形。
超過 15 萬節點改用 point sprite 之後才過關。

**三種畫法（20,000 節點）**

| 畫法 | FPS | 每幀 | 其中 JS |
|---|---|---|---|
| DOM element | 0.3 | 2,979 ms | 17.6 ms |
| Canvas 2D | 60 | 16.7 ms | 2.4 ms |
| WebGL Instanced | 60 | 16.7 ms | 3.7 ms |

最關鍵的一列是 DOM 那行的「每幀 2,979ms 但 JS 只有 17.6ms」——
**成本幾乎全在你的程式碼之外**（style / layout / paint），profile 自己的 JS 是看不到它的。

而 **Canvas 2D 在同樣兩萬節點也是 60fps**：畫不動是渲染層的問題，跟維度無關。
這條是整份研究最容易被誤讀的地方。

**降維（語意地圖）**

同一批向量、同一個演算法、同一組初始值，只有目標維度不同：
3D 的 kNN@10 鄰域保留率 **43.1%**，2D 是 **30.8%**，3D 高出 40.1%。

數學上 3D 明顯勝出——但結論仍是不引入，因為那份「最相似的八張」清單
是在 40 維空間算出來的，跟 3D 座標無關。把地圖整個拿掉，清單一字不差。
**量得到的優勢不等於使用者感受得到的優勢。**

## 執行

```bash
pnpm install
pnpm dev        # http://localhost:3400
pnpm build      # 產出 dist/ 靜態檔
pnpm preview    # 驗證 build 產物
```

**鍵盤**：`→` `←` 翻頁、`N` 展開完整說明、`T` 排練計時、`F` 全螢幕。
網址支援深連結（`#/10` 直接跳第 10 頁）。手機翻頁用底部的 `‹` `›`。

## 資料

`public/data/blueprint.json` 是**生成的**，可重跑：

```bash
node tools/generate-blueprint.mjs      # 2,331 個節點
node tools/generate-semantic-map.mjs   # 重算語意地圖（約兩分鐘）
```

節點的**文字**是生成的，**結構不是**——深度分佈、type 分佈、分支不均勻程度
都複製自一份真實的企業經營藍圖（2,331 節點／69 個根／深度 69-149-224-609-1280／
分支中位 2、最大 31）。

這件事會影響結論是否成立：佈局成本取決於**樹的形狀**而不是節點總數，
少數節點分支特別多才是 2D 佈局爆版的主因。用隨機散點會低估真實成本。

語意地圖的兩個指標（kNN@10 保留率、stress）是在這份生成資料上實際算出來的。

## 技術棧

Vite · React 19 · Three.js · React Three Fiber · Drei · Tailwind CSS v4 · Zustand

全場共用**單一 WebGL context**，切換投影片時只換 canvas 裡的 children——
避免 iframe 方案的黑畫面與 context 數量上限。
代價是相機變成全域狀態，每個場景都必須自己設定。

沒有後端、沒有 API、零外部請求，可完全離線執行。
